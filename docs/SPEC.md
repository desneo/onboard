# 产品规格

> 本文定义系统必须满足的业务能力、行为和边界，不描述具体代码结构。当前实现与使用方法见
> [`../README.md`](../README.md)，实现约束见 [`ARCHITECTURE.md`](ARCHITECTURE.md)，验收场景见
> [`TESTING.md`](TESTING.md)。

## 1. 系统定位

本系统是运行在无人机机载计算平台上的自主任务控制中心，负责：

- 连接 PX4 飞控并执行飞行动作；
- 管理本机、友机、地面站链路、任务和目标状态；
- 接收并执行地面站指令和任务；
- 编排反无人机任务；
- 与地面站及其他无人机通信；
- 上报运行状态和安全告警。

系统不实现飞控固件、地面站、摄像头驱动或中制导算法本身；中制导算法作为可信预编译库集成。

吊舱视频流中的检测和跟踪由导引头实现。机载程序完全移除 Perception 及图像相关能力，
不承担取图、图像预处理、视觉检测跟踪、图像推理或视频推流职责。

## 2. 运行环境

- 操作系统：Ubuntu 22.04；
- CPU 架构：x86_64、ARM64；
- 首要硬件平台：RK3588；
- 第一版本飞控：PX4；
- 飞控使用 UDP 且端口位于场景 02 的 PX4 远端端口 `14030`～`14039`、本地端口
  `14280`～`14289`，或旧 SITL 的 `14580`～`14589`（`1458*`）时判定为仿真飞机，
  判定结果通过 `AgentInfo.isSim` 上报。

运行主日志默认直接写入 `logs/plane.log`，不按日期创建子目录；重启后追加。
单文件达到 50 MB 后按序号轮转，历史文件为 `plane.1.log` 至 `plane.5.log`，超过保留数量淘汰最旧文件。
普通 `[info]` 日志按 `[logging].flush_interval_ms` 周期批量刷新，默认 1000 ms，须为正整数；
非法值导致配置加载失败并保留原有效配置。没有后续日志时也须按周期刷新已有内容。
`[warn]`、`[error]` 和任务、指令、自检的成功、失败、中止结束摘要立即刷新。
前台与 `--no-console` 模式使用相同策略；正常退出前刷新剩余日志。
这里的刷新指 `fflush`，使内容进入系统文件缓存并可被 `tail` 读取，不提供 `fsync` 的断电持久化保证。

### 2.1 机群部署

- 同一机群的板卡须能共用一份运行包和主配置。主配置的 `[deployment].profile` 必填且非空，
  随包默认选择捷联 A2416A 仿真预置。只运行一架飞机时，也使用包含该飞机的预置。
- 每次部署以完整运行包为唯一来源，部署配置从包内生成，预置须以包内相对路径引用实际随包文件。
  部署不读取或继承板端已有配置；程序、动态库、脚本、主配置、Zenoh 原生配置和全部预置全量同步，
  包外遗留部署文件删除，只保留运行目录的 `logs/` 及其中的 core。回退备份不作为配置来源。
- 完整运行包和配置引用必须在停止现有板端程序前校验，包无效时不得继续部署。
- 预置以飞机 ID 为节名，每架飞机配置唯一的板卡 IPv4 地址和飞控 URL，可配置吊舱型号、视频流地址和控制地址。启动时根据本机启用的非回环网卡 IPv4 地址唯一确定本机配置。
- 预置可用 `[groundstation]` 的 `ip` 配置一个地面站单播 IPv4，地址须与所有板卡地址不同。机载监听本机 `board_ip` 的 TCP `7447` 端口，主动连接配置的地面站和所有其他飞机。连接列表先列地面站，再按 IPv4 数值升序列出友机，跳过本机。
- 飞机身份、飞控和吊舱连接只从预置读取，Zenoh TCP 连接和监听端点由预置统一生成。
  仅有本机且地面站地址缺省时，连接列表由 Zenoh 原生配置处理。
- 主配置或预置无法读取、`profile` 缺失或为空、预置的飞机 ID 或板卡 IP 重复、必填项无效、
  无法匹配或匹配多架飞机时，程序记录原因并在启动飞控和 Zenoh 前退出。

### 2.2 开机自启和故障恢复

- 运行包支持在板端安装和卸载自启服务。安装时启动服务并登记开机自启，服务最早在系统开机满 10 秒时运行。
- 随包脚本支持后台服务和前台运行。主动停止服务取消待执行的重启，保留下一次开机自启。服务停止后可直接前台运行，应用日志同时输出到终端和日志文件。后台服务的应用日志只写日志文件。
- 服务模式下，崩溃或其他异常退出后等待 5 秒重启。60 秒内最多启动 5 次，超过限额进入失败状态，支持修复后重新启动服务。
- 安装时配置板端全局 core 路由，内核直接将 core 写入运行目录的 `logs/core/`，保留全部 core。卸载时移除服务管理的规则，在该规则仍生效时恢复安装前的路由，保留配置、日志和历史 core。

## 3. 飞控与状态

### 3.1 飞控连接

- 必须支持通过 UDP 或串口连接 PX4。
- 必须监测飞控连接建立、异常和恢复，并向业务模块提供当前链路状态。
- 飞控异常不得导致业务模块直接依赖 MAVSDK 或 PX4 细节。
- 必须将 MAVSDK 接收的 `STATUSTEXT` 以 `[info]` 写入运行日志，保留原始 `type` 和 `text`，不翻译飞控文本。
- 场景 02 与旧 SITL 判定为仿真时，必须持续提供 MAVSDK `GroundStation` 心跳，以满足 PX4 的 GCS 预检；其他连接保持 `CompanionComputer` 身份。

### 3.2 飞机状态

系统必须维护本机和通过机间通信获得的友机最新状态，包括：

- WGS84 经纬度、椭球高和相对起飞点高度；
- Roll、Pitch、Yaw；
- NED 速度和空速；
- 电压、飞行模式和飞控连接状态。

旧状态被新状态替代后不得继续作为当前状态使用。

友机上下线使用 Zenoh liveliness 存活标记感知，只在上线、下线及恢复上线时打印日志。
位置、速度等状态报文更新缓存并发布内部事件，不逐条打印；不增加基于状态报文的业务离线计时。

### 3.3 状态上报

- 必须按可配置周期向地面站和其他无人机发送本机状态。
- 必须向地面站上报当前任务状态、行为树和执行节点。
- 无任务时上报无任务；独立 Command 不产生 Task 状态。
- 必须依据最近收到地面站报文的时间维护地面站链路状态，超时阈值可配置。

## 4. Command 与 Task

### 4.1 控制模型

- 任意时刻最多执行一个 Task 或一个独立 Command。
- 不维护任务队列或指令队列。
- 新控制内容到达时，立即终止当前内容并执行最新内容。人工接管时优先终止当前执行，清理完成后允许新下发的内容启动。
- 起飞前自检仅在空闲时执行。自检期间拒绝新的普通飞行指令和任务，人工接管、`Disarm` 和 `StopMotor` 优先。
- 同一通信会话内，已处理的 `TaskInfo` 和 `Command` 按 `senderId`、`messageId` 去重，重传仍返回 `Ack`。

### 4.2 基础指令

必须支持：

- Arm、Disarm、Takeoff、Land、RTL；
- Waypoint、Route、Hover；
- StopMotor、SelfCheck。

补充规则：

- 未指定起飞高度时使用当前默认安全高度。
- NED 速度是机载内部控制能力，不允许地面站直接下发。
- 中制导支持 NED 速度和加速度前馈以及 Attitude Offboard。设定值必须校验、缓存，并以 50 ms 周期重发。
- StopMotor 只能由地面站人工触发，任务和其他机载模块不得自主触发。
- 指令完成必须依据实际状态判断，不能只依据指令下发成功。
- Route 航线飞行不设置执行超时，持续等待飞控任务进度完成；新的 Task 或 Command 仍可中止并替换当前航线。
- Route 开始前必须通过当前位置的临时非穿越航点调整到首航点的相对起飞点高度；未起飞时先自动解锁并起飞到默认安全高度。
- `SelfCheck` 由地面端向指定飞机单播。飞机须连接 PX4，在有效遥测中处于地面、已上锁且飞行模式为
  `Posctl`、`Altctl`、`Stabilized` 或 `Manual`。自检下发普通解锁，确认实际解锁后立即执行普通上锁。
  每个动作返回后最多等待 3 秒确认实际解锁状态。两次确认均完成时自检通过，起飞由后续指令触发。
- 解锁可能已生效但确认失败时，只有在同一飞控连接上确认飞机仍在地面且保有控制权时才尝试普通上锁。
  人工接管后停止自动动作。正常停机时满足同样条件则尽力恢复上锁。
- 每架飞机通过 `SelfCheckResult` 返回本次 `commandId`、是否通过和结果详情。无法确认恢复上锁时须明确说明。
  `Ack` 只确认接收。重传使用同一报文 ID 时只补发接收确认。

### 4.3 任务

- Task 表达任务意图，不包含 Command 序列或 BehaviorTree 结构。
- Task 只能由地面站下发，其他无人机不得向本机下发。
- 收到 Task 后必须返回接收确认；确认只表示已经收到。
- 必须支持使用匹配的任务 ID 中止当前任务。
- 任务步骤顺序执行；任一步骤失败后不得继续后续步骤。
- 任务状态包括待执行、执行中、完成、中止和失败。任务执行失败时须立即向 `sendToStation` 上报一次
  `TaskState`，包含本次 `taskId`、`status = "Failed"` 及已知的行为树和节点；随后周期上报无任务状态。

### 4.4 人工接管

- 人工接管始终优先于自动任务和指令。机载依据当前 PX4 连接上报的实际模式切换判定接管。每次飞控连接的首个有效模式建立基线，飞前处于 `Position` 可以正常启动任务。
- 执行中切入 `Position`（`Posctl`）或 `Stabilized` 时立即中止。执行中非预期进入 `Loiter`（`Hold`）时中止。机载下发 `Hold`、本次起飞达到目标高度或航点执行完成后的 `Hold` 可用于正常流程。疑似正常结束时暂停后续自动控制下发，最多等待 300 ms 核对本次完成遥测；此间切入 `Position` 或 `Stabilized` 时仍立即中止。QGroundControl 切入这些模式按相同规则判定。
- 同一次执行只中止一次。停止旧执行的飞控指令、重试和 Offboard 设定值下发，清理时保留飞控实际模式。随后拨动遥控器或收到旧控制报文均不恢复旧执行。
- 机载停止当前自动控制后记录一次接管操作日志，包含触发判定的前后模式 `previous`、`value`、停止自动控制操作，
  以及中止的 `taskId` 或 `commandId`。`Hold` 核对失败或超时时保留首次进入 `Hold` 的前序模式，不被核对期间的后续模式覆盖。
  机载向地面站发送 `Alert`，其中 `type = "manual_takeover"`，`detail` 与接管操作日志一致。任务同时上报
  `TaskState::Aborted`。同一次执行只记录一次接管操作日志和发送一次告警，地面站对同一告警只提示一次。

## 5. 反无人机任务

本版本恢复 `AntiUav` 的中制导阶段，不恢复本地视觉和末制导：

- 已在空中时直接进入 Midcourse；未在空中则按解锁状态执行 Arm／Takeoff 后进入 Midcourse；
- 指定 `targetTrackId` 时锁定该航迹；未指定时只允许自动锁定唯一候选，多个候选必须失败；
- 目标管理从进程启动起持续缓存每个航迹最近 20 帧；进入中制导后直接使用已有严格递增历史，不足时最长等待 30 秒，初始化参考点使用本机起始位置；聚合算法使用 `update_dt_s` 作为固定制导周期，历史与增量量测保留原始时间戳；
- `[midcourse].target_timeout_ms` 配置当前目标连续无有效更新的超时阈值，默认 5000 ms，必须为正整数。
  整个 Midcourse 阶段（含等待 20 帧历史）按该航迹最后一次被接受更新的本机单调接收时间计时，
  重复、乱序和其他航迹的数据不刷新计时；从未收到目标时从进入 Midcourse 起计时。
  进入时缓存已超过阈值须立即失败，不使用过期历史初始化；恰好等于阈值时仍运行，严格超过阈值后在下一次 BT tick 失败，
  失败 tick 不再调用算法或下发控制。目标更新超时不适用于 Arm／Takeoff；
- `[midcourse_algorithm]` 支持配置 `MidCourseConfig` 的全部字段。默认使用 INI 的水平速度、爬升速度、
  下降速度和指令加速度限值。
  设置 `use_px4_limits = true` 时使用 Flight Control 在连接后读取的 `MPC_XY_VEL_MAX`、`MPC_Z_VEL_MAX_UP`、
  `MPC_Z_VEL_MAX_DN`、`MPC_ACC_HOR_MAX` 缓存值。断连时缓存失效，重连后重新读取；
- `update_dt_s` 须与 `[behavior_tree].tick_interval_ms` 的秒值一致。省略时按行为树周期换算；
- 中制导应用 INI 或 PX4 限值后提前校验实际使用的 `MidCourseConfig`；20 帧历史就绪后调用聚合门面初始化，
  并在调用日志中记录完整生效配置。
  `MidcourseAlgorithm::init/updateTarget` 的每次调用均以 `[info]` 按调用顺序记录完整输入、
  返回值和原始 `error`；初始化历史逐帧保留。`update` 的完整输入输出按 2 Hz 成对记录，
  会话首次调用和调用失败时立即记录；有效控制输出包含实际指令类型及全部字段，
  `yaw_rad` 为空时明确记录 `nullopt`，`update` 失败时标记无有效输出，不重复附加会话号、调用号或更新号。
  每个 BT tick 将飞控实际航向由度转换为弧度传给算法，先调用 `update` 并下发控制，
  再按时间顺序用全部新雷达测量调用 `updateTarget`，使新估计在下一 tick 生效；
  机载不调用可选的只读诊断接口 `getTelemetry()`；
- 默认的 `VelocityAcceleration` 档下发 NED 速度、加速度前馈及航向，算法未提供期望航向时保持当前航向。
  `Attitude` 档下发由四元数和推力换算得到的姿态及推力设定值；
- 使用 PX4 限值时缓存未就绪，或配置校验、算法调用、输出校验或飞控下发错误时，
  整个 `AntiUav` 任务失败，停止 Offboard 并重置中制导会话。机载日志记录失败原因并向地面站上报任务失败状态；
- 第 21 帧前允许算法输出悬停。算法 `target_invalid_grace_s` 的预测宽限期默认 3 秒，
  宽限期结束后、机载目标更新超时前，继续执行算法返回的保持指令；
- 目标更新超时以明确的中文日志记录 `trackId`、未更新时长和实际配置阈值，
  进入时缓存已过期或从未收到目标时须明确说明。超时使整个 `AntiUav` 任务失败，停止 Offboard、清空设定值、
  重置中制导会话、取消目标需求并上报 `TaskState::Failed`；恢复收到目标数据不会恢复旧任务。
  30 秒历史初始化上限继续生效，目标更新超时可提前结束等待；
- 算法内部末端确认默认关闭。开启后，离轴角和弹轴角速率持续满足配置阈值时，算法进入确认状态并输出悬停设定值。
  机载持续执行中制导任务，直到目标更新超时、任务失败、Task Stop、新控制内容、人工接管或进程退出；
- Stop、任务替换、人工接管及异常退出必须停止 Offboard 下发、清空设定值并重置中制导会话。人工接管时保留飞控实际模式。

## 6. 图像职责边界与目标管理

### 6.1 图像能力移除范围

- 完全移除 Perception 实现、接口、事件和 DisabledPerception 占位实现。
- 移除机载图像采集、预处理、检测跟踪、画面叠加、编码及视频推流相关内容。
- 移除对应视觉插件管理、模型及算法配置、图像配置项、构建依赖和媒体测试要求。
- 保留通用 PluginManagement 模块，当前可为空实现，用于后续非图像插件扩展。
- 启动和部署不检查或安装图像模型、RKNN、视觉插件及媒体运行库。
- 导引头状态和人工机械控制由相机控制模块接入，末制导控制独立于该接口。

### 6.2 相机／吊舱控制

- 艾晟 ASD-2、中科 D80 使用 UDP 接收连续双轴速度、单轴归零和指定双轴角度指令。单轴归零保持另一轴的最新实测角，速度断流 500 ms 时停车。捷联 A2416A 为固定光轴，提供状态上报。
- `PodCommand` 使用指定飞机的 Zenoh 单播主题，与飞行任务独立。`PodState` 默认以 5 Hz 向地面站上报，型号特有信息使用中文键值对象，连续 1 秒无有效遥测时标记断开并清除过期测量。上报频率由 `camera.pod_state_report_hz` 配置。
- 相机控制接口处理控制帧和遥测帧。预置记录型号和控制地址，视频流地址通过 `AgentInfo` 上报。RK3588 实物串口接入扩展 `PodTransport`。

### 6.3 目标管理

- 本地目标管理不再订阅 Perception 检测事件或保存本地图像检测结果。
- 机载使用公共 `GcsTarget`，包含字符串航迹 ID `trackId`、Unix 毫秒时间戳 `timestamp_ms` 和 WGS84 位置 `geoPos`，其中 `altitude` 为海拔高度。
- 同一航迹只接受时间戳严格递增的数据，每个目标保留最近 20 条历史。
- 每个 `trackId` 首次收到有效目标时立即记录 `info`；后续每 20 秒由新有效数据触发一次汇总，
  包含最新 `timestamp_ms`、`history_size` 和自上次输出以来的更新数量，不重复计入已输出的首帧。
- `AntiUav` 任务创建成功后，从 Arm／Takeoff 阶段起监测所需目标。任务开始至少 2 秒后，
  连续 2 秒未收到该航迹有效更新时，每 2 秒记录一次 `info` 提示；无任务和独立 Command 不提示。
  提示包含 `trackId`、本机上次接收的可读时间及其时区偏移、原始 `timestamp_ms` 和实际未更新时长。
  从未收到时明确显示“从未收到”和 `timestamp_ms=<无>`，未更新时长从任务开始计算。
- 提示使用本机单调时间判断间隔，显示时间使用墙钟；任务开始前的陈旧缓存保留真实接收时间。
  其他航迹、非法、重复和乱序数据不刷新所需航迹的接收时间；有效更新恢复后重新计算 2 秒间隔。
  自动模式在锁定前仅观察唯一候选，多候选不误报缺失；实际锁定后只监测锁定航迹。
  任务停止、替换、人工接管、失败、完成或退出时停止提示。此提示仅记录本地日志，
  不改变现有初始化超时、任务控制及地面站告警行为。
- 雷达入口已提供 WGS84 坐标；本版本不做雷达坐标转换、视觉目标地理定位或轨迹平滑。

## 7. 通信

### 7.1 地面站

地面站至少能够下发指令、任务、任务中止、系统参数和目标信息，并获取：

- 本机状态；
- 当前任务状态；
- 系统告警；
- 任务接收确认。

视频流不由机载程序采集、处理或转发。

本机和友机的 `VehicleState.inair` 为布尔值，表示飞控报告的是否离地，默认 `false`。
本机状态直接取已有的飞控 `in_air` 遥测缓存，并随 `VehicleState` 广播。接收时缺少该字段取
`false`，字段存在但不是布尔值时解码失败；链路是否可用仍由 `fcLinkState` 表示。

机载收到合法 `TaskInfo` 或 `Command` 后交给任务调度，并向 `sendToStation` 返回 `Ack`。
`senderId` 用于标识发送方，机载按报文类型和内容处理控制消息。

配套 GCS 雷达入口默认监听 UDP `0.0.0.0:7790`，只处理 `radar_tracks`：

- 雷达 UDP 对外只有 `type=radar_tracks`、`schema_version=1` 一种协议报文，每个扫描周期发送一个完整数据报；
- `tracks` 为空、仅含 `state=coasting` 或同时含 `confirmed`/`coasting` 都是合法扫描；只发布 `state=confirmed` 的航迹；
- 忽略 schema 版本差异和未知字段，其他 `type` 不参与业务处理；
- 7790 只承载雷达扫描，不要求包含防守飞机航迹；友机坐标来自 Zenoh `VehicleState`；
- 友机状态按发送方缓存 3 秒，按 NED 速度外推到扫描时间，使用三维距离做全局一对一匹配；
- 50 米内实际匹配到的友机航迹被过滤，未匹配的 confirmed 航迹作为靶机发布；
- 友机没有出现在雷达扫描中不阻塞该帧；尚无友机状态或存在过期状态时整帧暂停转发；
- 靶机数据按公共 `GcsTarget` 尽力发布，不增加 Ack 或重发。雷达扫描中的径向速度和方位角作为额外字段忽略。

### 7.2 节点信息与主动查询

- 飞机和地面站以公共 `AgentInfo` 广播节点信息。机载填写 `agentId = planeId` 和 `agentType = Vehicle`，从配置读取 IP 和视频地址，从仿真判定读取 `isSim`。
- 机载先订阅 `sendToAll` 并注册查询接口，再声明 `plane/liveliness/{planeId}`。通信启动和发现其他节点上线或重连时，机载向 `sendToAll` 发布本机 `AgentInfo`，按存活标记去重。
- 机载接收并校验其他节点的 `AgentInfo`，要求 `agentId` 与信封的 `senderId` 一致。
- 支持 Zenoh 原生 get/queryable 查询 `queryToAgent/{agentId}/AgentInfo`，返回标准 `Message` 信封。查询失败时返回错误。
- 查询读取节点元数据，视频地址用于下游播放。

### 7.3 无人机间

- 第一版本支持最多 8 架无人机参与业务通信。
- 必须支持状态交换、指定飞机单播和面向其他节点的 `sendToAll`。
- `sendToAll` 表示投递给除本机外的节点，不要求使用网络层广播；无线通信优先单播。

### 7.4 可靠性

- 任务、指令等控制消息必须具备接收确认和可靠传输机制。
- 实时状态允许丢失，以最新有效状态为准，不逐条确认。

### 7.5 诊断信息上报

机载通过 `sendToStation` 发送 `Alert { type, detail }`，便于地面站粗略定位飞控与任务执行问题。
`detail` 使用中文描述，保留飞控原文、原始级别、API 名、错误枚举和已有字段名。

| `type` | 上报内容 |
| --- | --- |
| `flight_control_status_text` | 飞控 `Info` 及以上的 `status_text` 原始级别和完整文本，过滤 `Debug`。 |
| `command_started`、`command_finished` | 独立指令（含 `SelfCheck`）开始、完成、失败或中止，包含指令类型、`commandId` 和结果原因。 |
| `task_started`、`task_finished` | 任务开始和结束，包含任务类型、`taskId`、最终状态、已知行为树和节点及原因。结束包括完成、失败、显式停止、被新控制内容替换和人工接管。 |
| `flight_control_command_started` | 实际调用低频飞控操作前的动作名和关键参数，覆盖任务内动作、自检、航线上传和启动，以及 Offboard 启动、重启和停止；不展开完整航线。 |
| `flight_control_command_failed` | 飞控操作名和失败原因，保留 MAVSDK 原始结果，也包含未连接、参数无效等无法下发的原因。 |
| `flight_control_state_changed` | 首次连接、断开、恢复，以及实际模式、解锁/上锁、离地/着地变化。每次连接首份有效状态按当前状态上报，不误报为状态切换。 |
| `offboard_send_recovered` | 周期 Offboard 设定值接口从连续失败恢复成功；只表示接口恢复成功。 |

- 相同级别和文本的 `status_text` 在 5 秒内只报一次，不同文本或级别立即上报，重连重置去重状态。
- 周期 Offboard 速度、加速度、姿态和推力设定值不上报；连续发送失败只报首次和原因变化，恢复时报一次。
- 开始事件在仲裁通过、准备调用执行引擎时上报；同一次执行先报开始，再报至多一次结束。
  旧报文重传及迟到结果不重复产生生命周期事件；普通节点的派发错误、超时和明确失败原因必须进入结束详情。
- 保留 `TaskState`、`SelfCheckResult`、低电压、人工接管和指令失败上报。
  人工接管仍只产生一次 `manual_takeover`，并补齐对应执行的结束事件。
- Alert 由通信线程从最多 256 条的队列发送，允许缓存通信启动前的诊断。
  队列满时淘汰最旧消息并记录本地日志，停止后拒绝新入队。
  发送采用尽力发送，不增加持久化或断网历史补发；进程退出期间的诊断不保证送达。

## 8. 系统参数与安全

- 必须维护默认安全高度，支持启动配置和地面站运行时更新。
- 实机必须在飞控连接正常时监测低电压，并向地面站发送告警。
- 第一版本低电压只告警，不自动返航、降落、中止任务或接管友机任务。
- 仿真飞机不执行低电压告警。

## 9. 非目标

第一版本不要求：

- APM 飞控；
- Body 坐标系速度控制；
- 任务优先级、暂停恢复、队列或并行执行；
- 历史任务查询；
- 雷达坐标转换、目标轨迹平滑或视觉目标地理定位；
- 盘旋半径、电子围栏和禁飞区；
- 电量百分比；
- 固定 CPU、内存、延迟或吞吐量指标。
